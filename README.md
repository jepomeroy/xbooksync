# XBookSync

A browser extension that keeps your bookmarks in sync across Chrome and Firefox by
writing them to a storage target you control — a local file, a Git host, or object
storage — instead of a vendor account.

> **Status: early development.** The popup UI and the settings layer are in place.
> Bookmark reading/writing and the sync loop itself are still being implemented, and
> only the _Local File_ storage target is being worked on. Every other target renders a
> "not implemented yet" placeholder.

## Why

Chrome sync and Firefox Sync each keep bookmarks inside their own account silo, and
neither talks to the other. XBookSync treats the bookmark tree as a plain document that
gets serialized to a target of your choosing, so the same bookmarks can be shared
between browsers, versioned in Git, or backed up like any other file.

## Features

| Capability          | Notes                                                                                        |
| ------------------- | -------------------------------------------------------------------------------------------- |
| **Storage targets** | Local file (in progress) · GitHub repo · GitHub Gist · GitLab repo · S3 (all planned)        |
| **Sorting**         | Optionally sort bookmarks on sync, ascending or descending                                   |
| **Scheduled sync**  | Configurable sync interval, with the last sync time surfaced in the popup                    |
| **Manual sync**     | Sync-now button in the popup header                                                          |
| **Cross-browser**   | Built with [WXT](https://wxt.dev), targeting Chrome MV3 and Firefox MV2 from one source tree |

## Requirements

- [Bun](https://bun.sh) (the repo ships a `bun.lock`; npm or pnpm work too if you'd
  rather regenerate the lockfile)
- Chrome/Chromium or Firefox for development

## Getting started

```sh
bun install        # runs `wxt prepare` via postinstall, generating .wxt/
bun run dev        # launches Chrome with the extension loaded and HMR enabled
bun run dev:firefox
```

`wxt dev` opens a temporary browser profile with the extension already installed, so
there's no manual "load unpacked" step during development.

### Building

```sh
bun run build          # -> .output/chrome-mv3/
bun run build:firefox  # -> .output/firefox-mv2/
bun run zip            # packaged artifact for the Chrome Web Store
bun run zip:firefox    # packaged artifact for addons.mozilla.org
```

To load a production build by hand: `chrome://extensions` → enable _Developer mode_ →
_Load unpacked_ → pick `.output/chrome-mv3/`. On Firefox, use `about:debugging` →
_This Firefox_ → _Load Temporary Add-on_ and pick the `manifest.json` inside
`.output/firefox-mv2/`.

### Checks

```sh
bun run compile   # tsc --noEmit
bun run lint      # eslint .
bun run lint:fix
```

## Project layout

```
entrypoints/
  background.ts            # MV3 service worker: install-time defaults + popup message handling
  bookmarks/
    bookmarks.ts           # (stub) read/write the browser bookmark tree
    storage.ts             # (stub) StorageAdapter implementations
  shared/
    types.ts               # enums, the StorageAdapter contract, popup <-> background messages
    localsettings.ts       # typed wrappers around WXT's extension-local storage
  popup/
    App.tsx                # shell: header, panel switcher, sync-now button
    pages/                 # one component per bottom-nav panel
    components/            # settings widgets (storage, sort, sync, toggle)
assets/                    # bundled assets (app logo)
public/icon/               # extension icons, generated by @wxt-dev/auto-icons
wxt.config.ts              # WXT config; declares the `storage` and `bookmarks` permissions
```

WXT auto-imports common APIs (`browser`, `storage`, `defineBackground`, the React
hooks), which is why you'll see them used without an explicit import. The generated
declarations live in `.wxt/` and are refreshed by `wxt prepare`.

## Settings

All settings live in extension-local storage and are defined once in
`entrypoints/shared/localsettings.ts`. Defaults are written on install by the background
script.

| Key                      | Type            | Default      | Meaning                                   |
| ------------------------ | --------------- | ------------ | ----------------------------------------- |
| `local:storage`          | `StorageType`   | `File`       | Which storage target to sync with         |
| `local:storageFilePath`  | `string`        | `~/tmp` [^1] | Destination path for the _File_ target    |
| `local:sortBookmarks`    | `boolean`       | `false`      | Sort bookmarks before writing them out    |
| `local:sortOrder`        | `SortOrderType` | `Ascending`  | Sort direction, when sorting is on        |
| `local:syncEnabled`      | `boolean`       | `true`       | Master switch for syncing                 |
| `local:syncrate`         | `number`        | `900`        | Seconds between automatic syncs           |
| `local:lastSyncDateTime` | `string`        | Unix epoch   | ISO timestamp of the last successful sync |

[^1]: Hardcoded for testing; this should default to an empty string before release.

## Adding a storage target

Each target implements the `StorageAdapter` interface in
`entrypoints/shared/types.ts`:

```ts
interface StorageAdapter {
    readonly providerId: string
    hasChanged(knownVersion: string): Promise<{ changed: boolean; currentVersion: string }>
    read(): Promise<SyncData>
    write(content: string, previousVersion?: string): Promise<StorageMetadata>
}
```

`hasChanged` exists so the sync loop can poll cheaply — an ETag or commit SHA comparison
rather than a full download. `version` is deliberately opaque: whatever token the target
uses to identify a revision (ETag, commit SHA, MD5, content hash). To add a target,
implement the interface in `entrypoints/bookmarks/storage.ts`, add a variant to
`StorageType`, and add a case to `getStorageType` and to the `<select>` in
`entrypoints/popup/components/storage.tsx`.

## Code style

Prettier (4-space indent, no semicolons, single quotes, 120 columns) and ESLint with
`typescript-eslint` and `eslint-plugin-react-hooks`. Unused identifiers prefixed with `_`
are allowed, which is how handlers stubbed out ahead of their implementation stay lint
clean.
